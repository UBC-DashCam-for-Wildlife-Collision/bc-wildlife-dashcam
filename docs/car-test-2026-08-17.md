# In-Car Test — August 17, 2026

**For Claude Code running on the Pi.** Read this whole file, then execute the
steps in order. This is the first time the system is being tested mounted in
a vehicle, with the camera calibration also happening today for the first
time. `CLAUDE.md` has full project context if you need it.

**Hard safety constraint, applies to every step below:** any screen-watching,
typing, or debugging happens only with the car parked. Nothing here should
involve looking at a laptop or the Pi's display while the vehicle is moving.

---

## Power caveat — read before troubleshooting anything else

The Pi is running off a cigarette-lighter USB charger today, not the final
in-vehicle 12V→5V regulator (`docs/interface_contract.md` section 3). The
Pi 5 wants 5V/5A (25W) under load with the Hailo-8L actively running
inference — a lot of car chargers can't supply that.

If anything behaves strangely during testing — random reboots, the camera or
Hailo dropping out, the OLED misbehaving — run this **first**, before
assuming it's a software bug:

```
vcgencmd get_throttled
```

`0x0` means fine. Any non-zero value means an under-voltage or
thermal-throttle event has happened since boot. Treat that as a power
problem, not a code problem, and don't spend time debugging the pipeline
logic until it's ruled out.

## Step 1 — verify the deployed model is current

Check this hash against whatever is recorded as current for

whole session.

---

## Step 2 — checkerboard is confirmed correct, no further check needed

The printed calibration board is the official OpenCV 9x6-internal-corner
pattern (A4, from `opencv/opencv` doc), confirmed by physically counting the
printed squares: **7 × 10**, which is exactly right for a 9×6-corner board
(9 corners = 10 squares one way, 6 corners = 7 squares the other). Measured
square size: **23mm**. This is trustworthy — 10 squares × 23mm = 230mm fits
on A4's long (297mm) edge with margin, so the print did not scale down. Use
**23** for `--square-size-mm` below without re-verifying.

---

## Step 3 — capture calibration photos

Camera should already be in its final windshield-mounted position (doing
calibration mounted, not on a bench, means the calibration matches the real
deployed angle).

```
mkdir -p ~/calibration_photos
cd ~/calibration_photos
rpicam-still -o photo01.jpg
```

Repeat with incrementing filenames (`photo02.jpg`, `photo03.jpg`, ...) for
**15-20+ photos**, varying angle, distance, and position in frame each time.
Don't just hold the board flat-on and centered every time — tilt it, move it
to frame edges/corners, vary distance. That variety is what makes the
calibration math well-conditioned.

If manually re-running the capture command is tedious, write a quick
auto-capture loop (a photo every few seconds) so the person holding the
board just needs to reposition between beeps rather than run a command each
time.

---

## Step 4 — run calibration

```
source ~/hailo-rpi5-examples/venv_hailo_rpi_examples/bin/activate
python3 scripts/calibrate_camera.py ~/calibration_photos --square-size-mm 23
```

Check the printed **reprojection error** — want it well under 1.0px. If
it's high, that usually means too few photos or not enough angle variety;
worth retaking a handful before trusting the result.

Note the **focal length (fx)** value it prints — that's what step 5 needs.

---

## Step 5 — run the actual detection pipeline

```
python3 scripts/run_wildlife_detection.py --focal-length-px <fx from step 4> --live-alerts
```

`--live-alerts` fires the real LED bar, buzzer, and OLED — not simulated.
Without a real focal length passed in here, distance and zone output stays
meaningless, which is why step 4 has to happen first.

---

## Step 6 — what to watch for

- Detection quality against real road-perspective views — this is the first
  time testing outside indoor lighting / iPad-photo conditions (see the
  Aug 12 entry in `docs/meeting_log.md` for why that mattered: iPad glare
  and moiré made species accuracy unreliable there, and this is the first
  chance to see if a real camera view behaves differently).
- Whether LED / buzzer / OLED fire correctly when something enters a
  proximity zone.
- Whether the OLED holds its I2C connection through vehicle vibration. It
  dropped repeatedly on Aug 12 (`OSError: [Errno 121] Remote I/O error`
  from `adafruit_ssd1306`) — a known loose-connector issue, not expected to
  be fixed yet. If it drops again today, that's confirmation the physical
  fix (reseat/resolder) still needs doing, not a new bug.
